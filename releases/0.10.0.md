## What's Changed
### Added: spell checking in the prompt input

Claude Code can underline misspelled words in the prompt input as you type, but it ships no spell checker of its own — it drives one installed alongside it, and until now the image had none, so the feature could not be turned on at all. The base image now carries `hunspell` and its dictionaries, and every `agent run` enables spell checking wrapper-wide, so it works in every project with no per-project setup. English and Russian are recognised **together** by default: hunspell accepts a word found in any of the dictionaries loaded, so a prompt that mixes the two checks cleanly instead of underlining every word of one language. The trade-off of loading several dictionaries is that a typo which happens to be a valid word in one of the others is not flagged. Set `AGENT_SPELLCHECK=0` to turn the feature off, or `AGENT_SPELLCHECK_LANG` to replace the dictionary list — for example `AGENT_SPELLCHECK_LANG=en_GB,de_DE`, which needs one `agent rebuild --full` to install the new dictionaries before launches pick them up. Either variable, when set explicitly, wins over whatever the global settings file holds; left unset, edits you made there by hand are preserved. Requires one `agent rebuild --full` after upgrading. See [docs/configuration.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/configuration.md).

### Added: per-project startup scripts

A project that needs something to exist on the host *before* its container starts — most often a Docker network the agent then attaches to via `# agent-run-args: --network …` — previously had nowhere to put that step, leaving the user to run it by hand before every launch. An executable-bit-free `.claude-agent-wrap/startup.sh` now runs on every `agent run`, from the project directory, once `# agent-enable-startup: true` turns it on; the directive defaults to off and its value may instead be a positive number of seconds to replace the ten-second default budget. The interpreter comes from the script's own shebang, falling back to `/bin/sh`, so a CRLF checkout with its exec bits stripped still works. Any failure — a non-zero exit, the timeout expiring, an interpreter that cannot be executed — aborts the launch and releases the sidecars that launch had started, on the grounds that an agent whose prerequisites never materialized is worse than no agent. A timeout takes the script's whole process tree with it: the script runs in a session of its own, and the budget expiring sends `SIGTERM` to its process group and then `SIGKILL` five seconds later, so a script that shelled out to something slow cannot leave that something running — orphaned onto your terminal and, in the case of a `docker build`, still occupying the daemon — after the launch it was blocking has already been abandoned. Ctrl-C is relayed the same way and reported as a failed script, rather than escaping as a traceback. The one thing that escapes is a descendant which calls `setsid` for itself. The script runs as late as the pre-launch sequence allows while still holding the wrapper's startup lock, so two agents starting at once cannot race to create the same network; that lock is shared host-wide and its wait budget does not account for script runtime, which is why the default budget is deliberately small. It receives `AGENT_NAME`, `AGENT_INSTANCE_ID`, `AGENT_SIDECAR_NETWORK` and `AGENT_BINARY` on top of the host environment, the last being an absolute path to the `agent` executable for read-only verbs — `agent run` from inside the script would deadlock against the lock it is holding. stdin is closed so nothing can stall waiting for input, `agent run --base` skips the script along with every other project directive, and a script sitting there with nothing enabling it draws a warning rather than silently doing nothing. See [docs/docker-sandboxing.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/docker-sandboxing.md).

### Added: `agent inspect --lite`, for a report you can run from a startup script

`agent inspect` spends most of its wall clock on two things nobody needs every time: asking the npm registry whether a newer Claude Code exists, and walking the whole shared logs tree to total its size. That is fine at a terminal and wrong everywhere else — in particular inside a project [`startup.sh`](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/docker-sandboxing.md), which runs holding the host-global startup lock every other launching agent is queued behind. `-l`/`--lite` drops exactly those two steps and reports everything else: both container tables, every filesystem section, and the Claude Code version installed in each image. What it skipped is stated rather than implied — the logs footprint reads `not measured (--lite)` instead of going blank, `logs_bytes` and `latest_claude_version` are `null` in `--json` rather than `0`, and the report closes with a line naming both omissions. It combines with `-j`/`--json`. See [docs/shell-commands.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/shell-commands.md).

### Changed: the project Dockerfile moved to `.claude-agent-wrap/Dockerfile`

`Dockerfile.agent` was invisible to tooling: editors, linters and syntax highlighters pick the Dockerfile grammar by filename, and that name matched nothing, so the file every project customizes got no highlighting, no completion and no lint. Per-project wrapper assets now live in a `.claude-agent-wrap/` directory at the project root, with the image described by a plainly named `Dockerfile` inside it alongside the optional `startup.sh`. The build context is still the project root rather than that directory, so a `COPY pyproject.toml …` keeps working untouched, and `agent create` scaffolds the new layout. The old path still works and needs no migration today: it is read with a deprecation warning on every `agent run` and `agent rebuild`, and `mkdir -p .claude-agent-wrap && git mv Dockerfile.agent .claude-agent-wrap/Dockerfile` is the whole migration. Two things are deliberately strict rather than quiet — a project carrying *both* files is refused outright, since there is no way to guess which one was meant, and `# agent-enable-startup:` is rejected with an error when it appears in the legacy location instead of being silently ignored. Unlike the git-ignored `.claude/` state tree beside it, `.claude-agent-wrap/` is checked into the project, so a `.gitignore` holding a loose `.claude*` pattern will need narrowing. See [ops/dockerfile-agent-guide.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/ops/dockerfile-agent-guide.md).

### Changed: host paths for mounts declared in the project Dockerfile

A `# agent-run-args:` line can mount host paths into the container, and anything it named that did not yet exist was left to Docker to create — as `root`, leaving directories your agent could not write and you could not delete without `sudo`. Those host paths are now prepared before launch and owned by you: a writable bind source is created if it is missing, and a mount whose container-side target sits under `/workspace` also gets its mountpoint created inside the project, so the shadow-volume pattern (`-v /workspace/node_modules`) stops leaving root-owned directories behind after a run. A read-only source is the exception and is never invented — a `:ro` mount whose host path does not exist now fails the launch with an error naming the mount, instead of quietly mounting an empty directory whose emptiness only surfaces later inside the container; create the path, or drop `:ro` to have it created for you. Sources are read the way Docker reads them, so `/srv/data` and `./scratch` both count as host paths while `cache:/cache` stays a named volume, and `~` is still not expanded because no shell stands between the directive and Docker. The container side of a mount remains the image's own job: create and `chown` a custom mount path in your `.claude-agent-wrap/Dockerfile`, as `ops/dockerfile-agent-guide.md` now spells out. See `docs/docker-sandboxing.md`.

### Improved: `agent inspect` reports your project's own image, and reports it faster

The Claude Code version the report showed was the *base* image's, which is not the version you run in a project that customizes its image — and after an `agent rebuild --full` that never got as far as the project build, the two can differ by weeks with nothing saying so. The details table now carries a `project image` row directly under the base image whenever the current directory declares a `.claude-agent-wrap/Dockerfile`: the `claude-agent-<agent-name>` image `agent run` would actually launch here, whether it has been built at all, the Claude Code inside it, and whether that has fallen behind the registry. The registry is still consulted once for the whole report, and both images are compared against that one answer. A project that customizes nothing gets no such row, and a project Dockerfile that cannot be resolved — two competing files, a missing `# agent-name:` — now becomes a warning line on an otherwise complete report instead of aborting the one command you would reach for to diagnose it. Despite doing strictly more work, the report is faster: its Docker probes now run concurrently rather than one after another, so the wall clock is set by the slowest of them instead of their sum.
