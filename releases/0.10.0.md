## What's Changed
### Breaking: the wrapper runs on its own pinned CPython

`agent` no longer uses whatever `python3` your host happens to ship. It runs a CPython version this project pins, downloaded and checksum-verified by a new [bin/agent-bootstrap](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/bin/agent-bootstrap) script, and there is deliberately no fallback to a system interpreter — a fallback would mean the oldest distro anyone runs still decides which language features this code may use, which is the situation the change exists to end. After upgrading, run the bootstrap once per checkout:

```bash
/path/to/claude-agent-wrap/bin/agent-bootstrap
```

Until you do, `agent` exits non-zero and prints that command on stderr — that includes tab-completion, which simply falls back to filenames, and any programmatic caller, so a cron job or a symlinked `bin/agent` is refused the same way; the message also appears if the checkout is later moved, and the fix is the same. The interpreter lands in a git-ignored `.python/` inside the checkout, costs about 120 MB, and takes a couple of seconds. Nothing is ever pruned, deliberately — a logs viewer already running keeps executing from the tree it started on — so a future pin bump leaves the previous tree behind, and `rm -rf .python` followed by another bootstrap is both a clean reset and the way to reclaim that space. Hosts are now enumerated rather than assumed: glibc Linux and macOS, on x86_64 or aarch64/arm64. A musl host is refused by name, as is any other OS or architecture, so an Alpine host that ran 0.9.0 no longer works. `AGENT_PYTHON_TARBALL` points the bootstrap at an archive you staged yourself instead of downloading one, still verified against the pin — a path for air-gapped hosts, not a way around it. From here on `agent update` re-runs the bootstrap for itself, stopping the background logs viewer before it merges and leaving it stopped for the next `agent run` to bring back; a bootstrap that fails does not fail the update, so it names the command to re-run and leaves the working interpreter in place — which is exactly the state `agent inspect`'s new `interpreter` row flags, giving the running version, the pinned one and the fix, with `wrapper.python_version` and `wrapper.python_pinned` beside it in `--json`. The upshot for requirements is that Python leaves the list entirely: a host needs Docker, `tar`, something to download with (`curl` or `wget`) and something to hash with (`sha256sum`, `shasum` or `openssl`) — see [docs/getting-started.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/getting-started.md). Note that the version is pinned exactly rather than as a minimum, so [python-pin.env](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/python-pin.env) is the single place a future interpreter bump happens.

### Breaking: `agent update` refuses to run while agents are up

An update rewrites the checkout every live agent's host-side code runs from and re-provisions the interpreter underneath it, which is not something to do to a machine mid-flight. `agent update` now refuses outright while Docker reports any agent container or sidecar as running: it lists what it found and exits `1`, with nothing merged and nothing re-provisioned, and stopping those containers is the only way past it — there is no override flag, on purpose. The same refusal reaches the automatic check that `agent run` and `agent rebuild` perform on every invocation, and it is settled before the `y/N` prompt rather than after, so on a host with an update pending and one agent already up, a second `agent run` exits `1` instead of launching and `agent rebuild` exits `1` instead of building. Draining the fleet clears that; so does `AGENT_SKIP_UPDATE_CHECK`, which is read before anything else and therefore stops those two commands from consulting Docker at all — the switch for a host that runs agents continuously and takes its updates on its own schedule, rather than a way to update past the refusal, which `agent update` enforces regardless of it. A stopped container is ignored, including the corpse the Telegram sidecar keeps on purpose, and a host whose Docker daemon is unreachable counts as having nothing running. Once an update is going ahead it stops the `agent logs` background viewer before the fast-forward, so that long-lived process never spends the merge window executing newly merged code on an interpreter that has not been re-provisioned yet; it is not restarted for you, and until the next `agent run` brings it back the statusline falls back to telling you to run `agent logs`. An update with nothing to pull touches neither Docker nor the viewer. See [docs/shell-commands.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/shell-commands.md).

### Added: spell checking in the prompt input

Claude Code can underline misspelled words in the prompt input as you type, but it ships no spell checker of its own — it drives one installed alongside it, and until now the image had none, so the feature could not be turned on at all. The base image now carries `hunspell` and its dictionaries, and every `agent run` enables spell checking wrapper-wide, so it works in every project with no per-project setup. English and Russian are recognised **together** by default: hunspell accepts a word found in any of the dictionaries loaded, so a prompt that mixes the two checks cleanly instead of underlining every word of one language. The trade-off of loading several dictionaries is that a typo which happens to be a valid word in one of the others is not flagged. Set `AGENT_SPELLCHECK=0` to turn the feature off, or `AGENT_SPELLCHECK_LANG` to replace the dictionary list — for example `AGENT_SPELLCHECK_LANG=en_GB,de_DE`, which needs one `agent rebuild --full` to install the new dictionaries before launches pick them up. Either variable, when set explicitly, wins over whatever the global settings file holds; left unset, edits you made there by hand are preserved. Requires one `agent rebuild --full` after upgrading. See [docs/configuration.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/configuration.md).

### Added: per-project startup scripts

A project that needs something to exist on the host *before* its container starts — most often a Docker network the agent then attaches to via `# agent-run-args: --network …` — previously had nowhere to put that step, leaving the user to run it by hand before every launch. An executable-bit-free `.claude-agent-wrap/startup.sh` now runs on every `agent run`, from the project directory, once `# agent-enable-startup: true` turns it on; the directive defaults to off and its value may instead be a positive number of seconds to replace the ten-second default budget. The interpreter comes from the script's own shebang, falling back to `/bin/sh`, so a CRLF checkout with its exec bits stripped still works. Any failure — a non-zero exit, the timeout expiring, an interpreter that cannot be executed — aborts the launch and releases the sidecars that launch had started, on the grounds that an agent whose prerequisites never materialized is worse than no agent. A timeout takes the script's whole process tree with it: the script runs in a session of its own, and the budget expiring sends `SIGTERM` to its process group and then `SIGKILL` five seconds later, so a script that shelled out to something slow cannot leave that something running — orphaned onto your terminal and, in the case of a `docker build`, still occupying the daemon — after the launch it was blocking has already been abandoned. Ctrl-C is relayed the same way and reported as a failed script, rather than escaping as a traceback. The one thing that escapes is a descendant which calls `setsid` for itself. The script runs as late as the pre-launch sequence allows while still holding the wrapper's host-global sidecar lock, so two agents starting at once cannot race to create the same network; that lock is shared host-wide and its wait budget does not account for script runtime, which is why the default budget is deliberately small. It receives `AGENT_NAME`, `AGENT_INSTANCE_ID`, `AGENT_SIDECAR_NETWORK` and `AGENT_BINARY` on top of the host environment, the last being an absolute path to the `agent` executable for read-only verbs — `agent run` from inside the script would deadlock against the lock it is holding. stdin is closed so nothing can stall waiting for input, `agent run --base` skips the script along with every other project directive, and a script sitting there with nothing enabling it draws a warning rather than silently doing nothing. Note that this is a different trust proposition from the image it launches: the script runs on your host, outside the container, with your privileges, so audit `.claude-agent-wrap/` in full — the script as well as the Dockerfile's directives — before launching an agent in someone else's project. See [docs/docker-sandboxing.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/docker-sandboxing.md).

### Added: `agent inspect --lite`, for a report you can run from a startup script

`agent inspect` spends most of its wall clock on two things nobody needs every time: asking the npm registry whether a newer Claude Code exists, and walking the whole shared logs tree to total its size. That is fine at a terminal and wrong everywhere else — in particular inside a project `startup.sh`, which runs holding the host-global lock every other launching agent is queued behind. `-l`/`--lite` drops exactly those two steps and reports everything else: both container tables, every filesystem section, and the Claude Code version installed in each image. What it skipped is stated rather than implied — the logs footprint reads `not measured (--lite)` instead of going blank, `logs_bytes` and `latest_claude_version` are `null` in `--json` rather than `0`, a `lite` flag records which mode produced the document, and the report carries a line naming both omissions. It combines with `-j`/`--json`. See [docs/shell-commands.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/shell-commands.md).

### Added: the logs viewer starts itself on `agent run`

The statusline's `Today: ↑… ↓… | $…` segment is fed by a file only the `agent logs` background viewer maintains, so on any host where nobody had remembered to run that command the segment read `run \`agent logs\` for stats` instead — a manual step to repeat after every reboot, for a viewer that is a host-level singleton anyway. `agent run` now starts it, early enough that the viewer's initial walk of the log tree overlaps the image resolve, the secret prompts and the LiteLLM sidecar's own cold start rather than following them; the launch never waits for it and never fails because of it, since a viewer that cannot be started is a warning and nothing more. Nothing tears it down when the agent exits, which is the point — `agent logs --stop` remains the way to stop it. Two launches racing from a stopped state produce one viewer rather than two, a viewer that has been claimed but has not bound its port yet is reported as starting by both `agent logs` and `agent inspect` instead of being started a second time, and an agent running for hours leaves no zombie behind when the viewer stops first. The autostarted viewer always takes the default port 8765; `-p`/`--port` still directs a viewer you start by hand. Two launches skip the autostart: a headless `agent run` renders no statusline, and under `litellm-anthropic-sub` the statusline shows subscription rate limits, so the file has no reader either way — a custom provider declines the same way, by setting `autostart_logs_viewer` to `False`. `AGENT_AUTOSTART_LOGS=0` turns the whole thing off, and `agent inspect` grows a `logs viewer autostart` row under the viewer's own state — `logs_autostart` in `--json`, beside a new `starting` on the viewer itself — so none of this is guesswork: it reports `on`, or `OFF` naming whichever of the variable or the provider decided otherwise, and flags the one combination that silently does nothing — the variable set to `1` under a provider that declines — as `requested but IGNORED` rather than letting it read as a broken feature. See [docs/configuration.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/configuration.md).

### Changed: the project Dockerfile moved to `.claude-agent-wrap/Dockerfile`

`Dockerfile.agent` was invisible to tooling: editors, linters and syntax highlighters pick the Dockerfile grammar by filename, and that name matched nothing, so the file every project customizes got no highlighting, no completion and no lint. Per-project wrapper assets now live in a `.claude-agent-wrap/` directory at the project root, with the image described by a plainly named `Dockerfile` inside it alongside the optional `startup.sh`. The build context is still the project root rather than that directory, so a `COPY pyproject.toml …` keeps working untouched, and `agent create` scaffolds the new layout. The old path still works and needs no migration today: it is read with a deprecation warning on every `agent run`, `agent rebuild` and `agent inspect`, and `mkdir -p .claude-agent-wrap && git mv Dockerfile.agent .claude-agent-wrap/Dockerfile` is the whole migration. Three things are deliberately strict rather than quiet — a project carrying *both* files is refused outright, since there is no way to guess which one was meant; `# agent-enable-startup:` is rejected with an error when it appears in the legacy location instead of being silently ignored; and `agent create` refuses to scaffold a second Dockerfile beside a legacy one, naming the migration instead. Unlike the git-ignored `.claude/` state tree beside it, `.claude-agent-wrap/` is checked into the project, so a `.gitignore` holding a loose `.claude*` pattern will need narrowing. See [ops/dockerfile-agent-guide.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/ops/dockerfile-agent-guide.md).

### Changed: host paths for mounts declared in the project Dockerfile

A `# agent-run-args:` line can mount host paths into the container, and anything it named that did not yet exist was left to Docker to create — as `root`, leaving directories your agent could not write and you could not delete without `sudo`. Those host paths are now prepared before launch and owned by you: a writable bind source is created if it is missing, and a mount whose container-side target sits under `/workspace` also gets its mountpoint created inside the project, so the shadow-volume pattern (`-v /workspace/node_modules`) stops leaving root-owned directories behind after a run. A read-only source is the exception and is never invented — a `:ro` mount whose host path does not exist now fails the launch with an error naming the mount, instead of quietly mounting an empty directory whose emptiness only surfaces later inside the container; create the path, or drop `:ro` to have it created for you. `-v`/`--volume`, `--mount type=bind` and `--tmpfs` are all read, and sources are read the way Docker reads them, so `/srv/data` and `./scratch` both count as host paths while `cache:/cache` stays a named volume. A missing source is created as a *directory*, matching what Docker itself would do, so a single-file bind mount still has to exist beforehand. `~` is still not expanded, because no shell stands between the directive and Docker — and a source that starts with one now draws a warning saying so, naming the mount and asking for an absolute path, rather than being prepared under a literal `~` directory. The container side of a mount remains the image's own job: create and `chown` a custom mount path in your `.claude-agent-wrap/Dockerfile`, as `ops/dockerfile-agent-guide.md` now spells out. See [docs/docker-sandboxing.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/docker-sandboxing.md).

### Changed: the project Dockerfile validator follows the new layout

The validator is what `ops/dockerfile-agent-guide.md` tells an agent to run before it asks you to rebuild, and it knew only the old filename — so on a migrated project it reported a missing file and checked nothing. With no argument it now validates `.claude-agent-wrap/Dockerfile`, falling back to a deprecated `Dockerfile.agent` and warning when it lands there, and it stops with its file-missing exit code when both files exist or neither does rather than pretending the ambiguous case is simply absent. It also understands the new directive: `# agent-enable-startup:` in the legacy location is an error, `0` is an error that names `false` as the way to disable, and a bare `1` draws a warning because a number is always seconds — one second, not "true". A directive with no script beside it, a script with nothing enabling it, and a script with no shebang are each reported, and the run's summary now reports the startup script's state alongside the agent name and base image. See [ops/validate-dockerfile-agent](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/ops/validate-dockerfile-agent).

### Changed: `agent inspect` reports your project's own image

The Claude Code version the report showed was the *base* image's, which is not the version you run in a project that customizes its image — and after an `agent rebuild --full` that never got as far as the project build, the two can differ by weeks with nothing saying so. The details table now carries a `project image` row directly under the base image whenever the current directory declares a `.claude-agent-wrap/Dockerfile`: the `claude-agent-<agent-name>` image `agent run` would actually launch here, whether it has been built at all, the Claude Code inside it, and whether that has fallen behind the registry. The same facts arrive as a `project` object in `--json`. The registry is still consulted once for the whole report, and both images are compared against that one answer. A project that customizes nothing gets no such row, and a project Dockerfile that cannot be resolved — two competing files, a missing `# agent-name:` — now becomes a warning line on an otherwise complete report instead of aborting the one command you would reach for to diagnose it. Despite doing strictly more work, the report comes back faster. See [docs/shell-commands.md](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/docs/shell-commands.md).

### Changed: errors and warnings carry a severity tag

When a launch aborts, the one line explaining why used to print in the terminal's default colour, indistinguishable from everything above it — worst of all for a project `.claude-agent-wrap/startup.sh` that overran its budget, where that line arrives after however much output the script itself streamed. Errors now print bold red on a terminal, alongside the yellow warnings and green successes already in use, and every one of them opens with `[ERROR]` — every warning with `[WARNING]` — so the severity survives being redirected or piped, which is exactly when colour is stripped and when you are most likely reading the output after the fact. A message spanning more than one line aligns its continuations under the tag, and the assorted `Error:`, `error:`, `usage:` and `note:` prefixes that individual messages used to carry are gone, since they would only have doubled it. A sidecar that aborts a launch by exiting on the spot — a failed image pull, a declared `--network` that does not exist, a recorded port it cannot read back — now reports through that same channel instead of printing plain. Three commands moved messages between streams to match what those messages are: `agent inspect` puts the warnings its report can end with on stderr rather than appending them to the report itself, so a redirected report holds only the report, with `--json` unchanged and the warnings still part of the object it prints; `agent secrets check` keeps every row on stdout with its columns intact instead of splitting `OK` and `MISSING` across two streams, and closes with a single error naming how many secrets are missing and the `agent secrets set` that fixes them, at the same exit status as before; and `agent stats` stops reporting an empty result as a failure, so no registered projects or a `--pattern` matching nothing is plain text on stdout, matching the success it already exited with, while conflicting `--from`, `--until` and `--days` bounds or an unparseable `--pattern` regex remain errors and still exit non-zero. Two things that were never errors have left that channel as well: `agent` with no arguments prints its command listing on stdout, so `agent | less` works, and the prompt for a secret now goes straight to the terminal, surviving a discarded stderr.

### Changed: attribution rules for the agents in your projects

The [`default-CLAUDE.md`](https://github.com/mayty/claude-agent-wrap/blob/0.10.0/ops/default-CLAUDE.md) shipped to consumer projects tells every agent to mark the files it writes with an AI-attribution line, and the old wording keyed that line to the action — `created` when creating, `edited` when editing — which quietly produced a second line each time an agent edited a file it had created earlier. The rule now keys on the file's state instead: a file carrying no line gets `created` if the agent is creating it and `edited` if it is editing one that already existed, and a file that already carries a line is left exactly as it is. Stacking two lines is forbidden outright, since a `created` line already covers every later edit, and rewriting `created` into `edited` stays forbidden as before. Generated output is newly exempt: when an agent writes a script, template or codegen step whose job is to emit files, the generator carries the line and the files it emits carry none — but that covers only what a program produces as its normal output, so creating or rewriting a file with `sed`, a heredoc or a throwaway one-off script still counts as authoring it and takes a line. Formats that disallow comments, JSON among them, skip attribution entirely. Because `agent update` replaces an unmodified copy of the file, this arrives with the upgrade; a copy you have customized is left untouched, as always.
